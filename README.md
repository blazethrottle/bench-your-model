# LLM 벤치마커

구독으로 쓰는 Claude와 Grok 모델에 같은 과제, 같은 채점 규칙을 적용해 작업별 기준표를 만드는 개인용 웹 서비스입니다. 인터넷 속도 측정처럼 시작 버튼을 누르면 분류별 점수와 종합 점수가 나옵니다.

## 켜는 방법

`벤치마커 시작.command` 파일을 두 번 누릅니다. 터미널 창이 열리고 브라우저에 `http://127.0.0.1:4173` 이 열립니다. 터미널 창을 닫으면 서비스가 꺼집니다.

## 동작 방식

- 이 Mac에 설치된 `claude`, `grok` 명령줄 도구를 직접 호출합니다. 두 도구의 구독 로그인을 그대로 쓰므로 API 키가 필요 없습니다.
- 그래서 이 서비스는 이 Mac 안에서만 동작합니다(주소 `127.0.0.1`). 인터넷에 올리면 구독 계정이 외부에 노출되므로 클라우드 배포를 하지 않습니다.
- 측정 환경은 두 가지입니다.
  - 실사용 환경(기본): 사용자의 지침, 스킬, 도구가 모두 붙은 상태. 모델의 파일 쓰기는 측정용 임시 폴더로 제한합니다.
  - 순수 모델: 지침과 도구를 뺀 모델 자체.
- 결과는 `data/runs/` 에 측정 한 번당 파일 하나로 저장됩니다.

## 측정 분류와 깊이

분류는 아홉 개다: 코딩, 디버깅, 리서치(자료 분석), 플래닝, 반복업무 정확도, 추론과 계산, 기획, 창의력, 이미지 제작(SVG 코드).

| 깊이 | 과제 | 성격 |
|---|---|---|
| 빠른 측정 | 9개 (분류당 1개) | 한 번의 요청으로 끝나는 과제 |
| 정밀 측정 | 33개 | 위와 같은 종류 전체 |
| 고난도 측정 | 3개 | 작업 폴더를 받아 여러 단계로 수행하는 긴 작업. 과제당 최대 20분 |

- 정답이 있는 과제는 숨은 테스트나 규칙으로 채점한다.
- 기획과 창의력은 형식 규칙 검사에 더해, Claude 모델 하나와 Grok 모델 하나가 작성자를 모르는 상태로 채점한다.
- 고난도 과제는 다음 세 개다.
  - 결함 수정: 파일 10개짜리 프로젝트에 심어 둔 결함 10개를 명세와 대조해 고친다. 공개 테스트는 일부만 확인하고, 채점은 숨은 입력 885건으로 한다. 손대지 않으면 0점이고 기존 동작을 망가뜨리면 감점이다.
  - 결함 검토: 다른 결함 12개의 위치를 보고한다. 찾은 비율로 채점하고 틀린 보고가 많으면 감점이다.
  - 일정 최적화: 정답이 없는 과제다. 풀이 프로그램을 작성하면, 그 프로그램을 숨은 문제 여섯 개에 호출당 2초 제한으로 실행해 일정의 품질로 채점한다. 긴 시간을 들여 찾은 기준 일정과의 비율이 점수이므로 만점에 몰리지 않는다.

## 측정 변수

- 모델: `config.json` 의 목록에서 고른다. 설치된 `claude` 가 아직 모르는 새 모델은 `behavesAs` 에 기존 모델 이름을 적어 등록한다.
- 추론 강도: 기본값, low, medium, high, xhigh. 여러 개를 고르면 모델 × 강도 조합마다 따로 측정한다.
- 반복 횟수: 1회 또는 3회. 3회면 기준표에 중앙값과 점수 범위를 표시한다.
- 측정 환경: 실사용 환경과 순수 모델.

## 2026-11-11까지의 측정에서 확인한 것

표본이 작다(조합당 1~2회). 방향을 보는 용도이고 순위를 확정하는 근거는 아니다.

- 요구 사항이 명확하고 정답이 있는 과제는 가장 가벼운 모델(Claude Haiku 5.5)도 만점을 받았다. 한 번에 끝나는 과제 33개 수준은 물론이고, 대용량 입력을 요구하는 알고리즘 8문제, 프로젝트 결함 10개 수정, 결함 12개 검토까지 두 번씩 100점이었다. Claude Opus 5.5도 같은 점수였다. 이런 과제에서 갈리는 것은 시간, 토큰, 비용이다.
- 정답이 없는 최적화 과제에서는 차이가 났다. Haiku 5.5는 83점과 88점(2~4.5분), Opus 5.5는 96점과 98점(20분을 모두 사용)이었다.
- Grok 4.7은 기본 추론 강도에서 고난도 과제 세 개 모두 20분 안에 끝내지 못했다. 세션 기록상 그 시간의 대부분이 추론 단계였다. 결함 수정 과제는 폴더에 남긴 파일 기준으로 결함 10개를 모두 고쳤지만, 나머지 두 과제는 결과물이 없었다.
- 추론 강도를 low로 낮추면 Grok도 정답 과제를 끝냈다. Grok 4.7은 결함 수정과 결함 검토에서 100점(각 약 8분), Grok 4.5도 100점(각 약 4분)이었다. 최적화 과제는 Grok 4.7이 80점(20분 초과, 남긴 풀이로 채점), Grok 4.5가 75점(약 15분)이었다.
- 최적화 과제의 점수를 한 줄로 놓으면 Opus 5.5 (96, 98) > Haiku 5.5 (83, 88) > Grok 4.7 low (80) > Grok 4.5 low (75) > Grok 4.7 기본 강도 (0, 0)이다. Grok 쪽은 1회 측정이다.
- 같은 모델, 같은 과제, 같은 점수에서도 입력 토큰은 12만에서 76만까지 흔들렸다. 자원 사용량을 비교하려면 반복 측정이 필요하다.

## 설정

`config.json` 에서 모델 목록, 심사 모델, 과제당 제한 시간, 동시에 측정할 모델 수를 바꿉니다. 새 모델이 나오면 `models` 에 한 줄을 추가합니다.

## 검증

```bash
npm test
```

채점기 자체를 검증합니다. 기준 답안이 만점을 받는지, 무의미한 답이 저점을 받는지, 디버깅 과제의 버그 원본이 탈락하는지, 모델이 쓴 코드를 실행하는 격리 프로세스가 파일 쓰기와 무한 반복을 막는지 확인합니다.

## 안전 장치

- 서버는 `127.0.0.1` 에만 열리고, 다른 이름이나 다른 사이트에서 온 요청은 거부합니다.
- 화면에서 고를 수 있는 모델은 `config.json` 에 적힌 것뿐이며, 명령은 셸을 거치지 않고 인자 배열로 실행합니다.
- 모델이 쓴 코드는 파일 쓰기, 다른 프로그램 실행, 환경 변수 접근, 네트워크 접속이 막힌 별도 Node 프로세스에서 5초 제한으로 실행합니다. 그 프로세스에는 입력값만 전달하고 정답은 전달하지 않으며, 정답 비교는 바깥에서 합니다. 실행 결과는 실행할 때마다 새로 만드는 일회용 표식이 붙은 줄만 인정합니다. 네트워크를 차단할 수단이 없는 환경에서는 모델이 쓴 코드를 실행하지 않습니다.
